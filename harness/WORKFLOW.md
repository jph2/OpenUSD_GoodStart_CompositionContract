# Working method

1. Read the agent entry and current state. Identify the requested output and exact scope: discussion, contract change, profile, inspection or authorized repair.
2. Select the relevant CC rules and bounded sources. Record whether each claim is a mechanism, published pattern, proposal or observed result.
3. Describe expected behavior and counterexamples. Resolve rightful ownership and conditional context before choosing a destination layer.
4. Update the human-readable proposal first when semantics change. Preserve CC IDs; document disagreements in DISCUSSION.md. Mark future capabilities as planned. Review and update the reusable composition skill for every repository change under AGENTS.md; keep its version equal to the contract and refresh its generated reference and managed installation.
5. For eventual tooling, use versioned inputs and deterministic USD APIs. Separate discovery, planning, candidate comparison and applying a repair. Follow TOOLING_REQUIREMENTS.md; no executable CLI exists yet.
6. Report what changed and what evidence was actually inspected. Run tests only when requested; a documentation edit is not evidence that composition or Omniverse behavior has been verified.
7. Update STATE.md and relevant roadmap decisions. Keep the next step concrete and distinguish incomplete work from blockers.

The [controlled-workflow guide](https://haluszka.com/ai-harness-quickstart/guide/agents-skills-workflows.html) motivates promoting repeatable structural work into scripts. Human/LLM interpretation remains useful for ambiguous requirements and alternatives; neither substitutes for observed composition results.
