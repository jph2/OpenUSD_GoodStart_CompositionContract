# Deterministic tooling requirements

**Draft 0.1. All capabilities below are planned, not implemented.**

The 0.1.1 example adds `tools/build_example.py`, a bounded author for a new fixture directory. It uses OpenUSD 26.08, refuses nonempty output, records files/hashes and reads back the five saved default entrypoints. This supplies preliminary fixture evidence for DT-01; it does not implement the general DT-01–09 core, enumerate inactive opinions, classify arbitrary scenes or certify the fixture. Example-specific JSON documents are draft inputs, not an accepted general schema.

We need repeatable scripts as the execution foundation. An LLM may explain findings or propose an ownership decision; it must not improvise USD repair operations for each run. A UI, MCP bridge or pipeline node should call the same core.

| ID | Requirement | Future acceptance evidence |
|---|---|---|
| DT-01 | Reproducible inputs: identify stage, contract/profile revision, USD version, resolver, dependencies, load rules, variants, session state and time range. | Same declared inputs produce equivalent stable reports, with volatile run metadata separate. |
| DT-02 | Read-only inventory through USD/Sdf APIs: authored specs and composed contributions, fields, selections, variant context, operation order, bindings, samples and provenance. | Inventory covers supplied fixtures; unavailable dependencies and excluded states are explicit. |
| DT-03 | Rule classification: apply CC IDs and explicit ownership/profile mappings; ambiguity becomes a finding, not a guessed repair. | Each finding identifies source, destination if known, rule, evidence and uncertainty. |
| DT-04 | Dry-run plan: exact field-level changes, affected dependencies, expected effect, conflict handling and preconditions; no source mutation. | Source content stays unchanged and a reviewer can reconstruct the proposed edits. |
| DT-05 | USD-aware candidate repair: preserve variant context, relative path anchoring, metadata/list operations and coherent transform operations/order. For composed packages, create/register the rightful TransLyr when an ordinary transform is needed; keep a needed intrinsic leaf transform inline. | Candidate and source-removal effects considered together; no flattening or collateral field deletion. |
| DT-06 | Explicit execution authorization; revision checks, rollback and audit for multi-file edits. | Interrupted/conflicting operations leave recoverable state; repeat application is idempotent. |
| DT-07 | Compare expected composed behavior across declared configurations, samples and load contexts. | Transforms, selections and resolved materials match expected outcomes or documented intentional changes; incomplete coverage is visible. |
| DT-08 | Shared core independent of Omniverse UI, agents and private pipeline backend. | Local standalone invocation and adapter invocation use the same input/output contract. |
| DT-09 | Bounded operation and reporting: deterministic ordering, explicit limits/errors, machine-readable findings plus readable summaries. | No silent skipped assets, swallowed failures or accidental whole-repository scans. |

These requirements elaborate CC-17 through CC-23. Future fixtures should include direct local opinions masking variants, parent/child placement, inactive branches, missing dependencies, referenced relative paths, animation ownership and conflicting destination fields. Tests are planned work requiring an implementation task; none are claimed here.

## Workbench and bulk cleanup delivery

CW-05 adds an embedded USDA scene editor in a dockable Omniverse panel. It shares source identity and revision handling with CW-01 and authored-spec navigation with the integrated CW-03 workflow. Require distinct text-buffer, in-memory Apply and persistent Save states, candidate parsing, stale-buffer detection, recoverable undo and explicit representation/format handling. It edits scene description and provides no script-execution function. Detailed requirements and proposed acceptance are in the [editor roadmap](../ROADMAP.md#cw-05--embedded-usda-scene-editor).

The [composition workbench roadmap](../ROADMAP.md#8-source-editing-and-composition-workbench) now defines CW-03 as one integrated Opinion inspection, routing and contract-guided migration capability; the former separate CW-04 migration feature is folded into it. CW-03 uses DT-01–09 end to end: inventory and classification (DT-01–03), plan and candidate edits (DT-04/05), authorization/recovery and behavior comparison (DT-06/07), shared UI-independent core and bounded reporting (DT-08/09). The Kit extension is the interactive front end; IDE/CLI adapters call the same core. Detailed UI and acceptance requirements remain planned; no general inspector, router, migration implementation or extension is claimed.

The integrated CW-03 capability includes a versioned catalogue of cleanup/routing recipes and resumable decision checkpoints. Under DT-03/04/06, unresolved ownership, destination/context, collision or behavior intent must produce a scoped needs-decision record before the affected edits are applied. Authorized unambiguous groups may execute under the declared batch policy. Persist decisions and source revisions; re-plan after decisions or changed inputs. Unattended invocation returns unresolved work explicitly. See the [checkpoint requirements](../ROADMAP.md#reusable-cleanup-scripts-and-decision-checkpoints) for grouping, recovery and proposed acceptance.

CW-02 is a source-aware application launcher: resolve the chosen reference/payload arc or sublayer row to the exact source, identify whether the user is opening a layer, asset entrypoint, referenced prim or composed preview, and launch only a configured, verified application adapter. Track app/build/plugin/resolver capabilities, source revisions and parent reload state; DCC USD support is not assumed to round-trip every schema or composition feature.

CW-06 adds prim-scoped publish-and-recompose workflows. Reuse DT-01–09 for source inventory, dependencies, identity, revision checks, plans, recovery and comparison. Keep composition-preserving output, flattened snapshot, file encoding and USDZ packaging as explicit separate choices; USDZ is a constrained package, not ordinary ZIP. A prim-level recompose action offers Reference or Payload. Sublayers compose whole LayerStacks, so full-layer contribution requires a separate operation. A versioned target-paradigm registry carries a profile's source/revision, domain, output recipe, resolver/runtime, validator, exclusions and acceptance evidence. It must not claim universal equivalence or conformance from a label alone. The initial registry entries and gating rules are in the [CW-06 roadmap](../ROADMAP.md#cw-06--publish-selected-prim-as-an-asset); no publisher or application extension is implemented.

## Pipeline-to-composition handoff

**Contract boundary:** [CC-29](../CompositionContract.md#24-pipeline-generated-startpoints-and-target-authoring) defines the source-pipeline → generated USD startpoint → composition contract → target-application handoff. A pipeline is an optional producer. It emits persisted USD plus a typed/versioned manifest and report; the composition profile declares layer/asset ownership, arcs, strength and target acceptance. The downstream scene remains inspectable without the producer UI/runtime.

For any producer adapter, require immutable Source identity/revision and a separate explicit Target; output hashes and dependency closure; governing IDs and source-to-USD mappings; USD/runtime/schema versions; units/up-axis; declared profile and layer/prim destinations; diagnostics; and a saved-stage read-back. Regeneration may update only producer-owned outputs after revision checks and candidate-versus-current comparison. Preserve target-application layers, surface overlaps and require a reviewed plan for namespace/identity/binding changes. A pipeline execution or manifest alone does not prove USD composition or consumer correctness.

A bounded source review of `OpenUSD_GoodStart_Pipeline_nodes` read its Horizon Map, Composition Pipeline Vision, relevant Roadmap item WP-E108 and USD BRep research. It did not inspect the full implementation, verify licensing/API compatibility, run the extension/nodes, or establish persisted Omniverse acceptance. Treat it as the current optional candidate only; no private code or credentials are included here. Any future adapter must meet DT-01–09/CC-29 and remain replaceable.

The sibling BRep research proposes one BRep Tessellate node before considering separate Primitive and Boolean operations. NVIDIA's [USD BRep project](https://github.com/NVIDIA-Omniverse/usd-brep) uses an `omniSolid` schema plugin for its BrepArray representation and supports NURBS-based boundary representation; this plugin/runtime is not baseline OpenUSD geometry support. Keep solid, USD BrepArray and tessellated mesh artifacts typed separately, versioned, unit-aware and independently validated. BRep roadmap WP-E108 remains deferred in the owning repository; this contract adds no node IDs or implementation scope.
